# AI Conversation → Summary → Diagnostic Flow

## How It Works

Every patient-facing visit at an AI-enabled location flows through three discrete artifacts produced by separate AI calls, with the **patient gating the doctor queue** in both nurse-enabled and non-nurse-enabled flows.

### The three artifacts

1. **AI conversation** — patient chats with the intake AI (`ai-conversation` edge function streaming Claude/Gemini/OpenAI per location tier). The AI gathers chief complaint, onset, duration, severity, medications, allergies, chronic conditions, pets, etc. Conversation ends when the AI emits the literal token `[CONVERSATION_COMPLETE]`.

2. **AI summary** — a transcript-derived plain-text paragraph describing what the patient said. **Pure transcript content; nurse vitals/notes are NOT injected here.** Generated by `generate-summary` edge function, saved to `visits.ai_summary`. The patient sees this on the summary review screen and must approve before the visit enters the doctor queue.

3. **AI diagnostic** — a doctor-only suggestion (`{diagnosis, reasoning}` JSON) derived from the summary + patient medical records + nurse vitals + nurse notes. Generated by the same `generate-summary` edge function, saved to `visits.ai_diagnostic`. The diagnostic fires at a deferred time so it always has the most complete data.

### Trigger → logic → outcome

`generate-summary` accepts a `mode` parameter (`"full" | "summary_only" | "diagnostic_only"`, default `"full"`) that controls which artifacts it produces:

| Trigger | Mode | When | Why |
|---|---|---|---|
| `ai-conversation` on `[CONVERSATION_COMPLETE]`, non-nurse location | `full` | Immediately on AI complete | No nurse data is coming, generate both at once |
| `ai-conversation` on `[CONVERSATION_COMPLETE]`, nurse-enabled location | `summary_only` | Immediately on AI complete | Patient needs the summary to approve. Diagnostic deferred until nurse vitals are in. |
| `nurse_release_to_doctor` after vitals + notes recorded | `diagnostic_only` | Right after nurse releases | `nurse_reviewed=true`, vitals + notes available — diagnostic fires with full clinical picture |
| `claim_patient` when doctor (no nurse role at location) claims a nurse-enabled visit with no diagnostic yet | `diagnostic_only` | On doctor-direct claim | Doctor bypassed nurse triage; diagnostic runs without nurse data so doctor isn't stuck without one |
| `claim_patient` fallback if `ai_summary` somehow missing | `full` | On any claim with NULL summary | Self-healing for failed earlier generate-summary calls |

### Patient approval gates the queue (Rule A)

In **both** flows (nurse-enabled and non-nurse), the visit's `status` stays `still_answering_ai` until the patient hits Submit on the summary review screen. `approve_summary` then flips status to `waiting_doctor_claim` (or `awaiting_arrival` for arrival-mode check-ins). Only then can a nurse or doctor claim. This was a behavioral change from the previous nurse-enabled auto-queue (which made the patient's Submit button ornamental).

### Diagnostic content

The diagnostic prompt receives:
- Patient demographics (age, sex)
- Location specialty
- Active medical records: medications, allergies, chronic conditions, pets
- Past visit summaries (last 10)
- The AI summary
- The full transcript
- **Nurse notes** (`visits.nurse_notes`) — only if `nurse_reviewed = true`, else `"None recorded"`
- **Nurse vitals** (via `get_visit_vitals_text` RPC) — only if `nurse_reviewed = true`, else `"None recorded"`

This means: doctor sees a diagnostic that incorporates a BP 180/110 reading the nurse took, not one frozen at the moment of conversation completion.

## Files That Represent It

### Edge functions
- `supabase/functions/ai-conversation/index.ts` — streams Claude responses to patient, detects `[CONVERSATION_COMPLETE]`, fires `generate-summary` with appropriate `mode`.
- `supabase/functions/generate-summary/index.ts` — mode-aware. Generates summary (skipping diagnostic in `summary_only`), generates diagnostic (skipping summary in `diagnostic_only`), both in `full`. Idempotent for `summary_only` (no-ops if `ai_summary` already exists). Requires existing `ai_summary` for `diagnostic_only`.

### SQL functions
- `sql/start_ai_conversation.core-sql` — builds the AI's system prompt including the `CONVERSATION END PROTOCOL` block that mandates the `[CONVERSATION_COMPLETE]` marker and forbids inline summaries.
- `sql/save_summary.core-sql` — service-role-only RPC that writes `ai_summary`, `ai_structured_card`, `ai_diagnostic`, `ai_completed_at`. Called by generate-summary.
- `sql/get_conversation.core-sql` — returns visit messages. Service-role gets all (including system prompt); patient gets all except first system row. Has tie-breaker on `id ASC` so cached prefix vs greeting ordering is stable when both rows share a microsecond timestamp.
- `sql/approve_summary.core-sql` — strict status guard (`still_answering_ai` only). Sets `patient_approved`, `patient_approved_at`, flips status to `waiting_doctor_claim` or `awaiting_arrival` based on `checkin_mode`.
- `sql/reject_summary.core-sql` — clears `ai_summary`, `ai_structured_card`, `ai_diagnostic`, `ai_completed_at`; re-opens conversation with a system message hint.
- `sql/claim_patient.core-sql` — two recovery triggers: backwards-compat `mode: full` if `ai_summary` is somehow NULL, and Rule C `mode: diagnostic_only` when a doctor-only role claims a nurse-enabled visit with no diagnostic.
- `sql/nurse_release_to_doctor.core-sql` — sets `nurse_reviewed = true` + `nurse_notes`, then fires `generate-summary` with `mode: diagnostic_only` so the diagnostic regenerates with nurse data.
- `sql/move_to_queue_on_error.core-sql` — fallback when AI conversation hits an error or 60s frontend timeout fires — flips status to `waiting_doctor_claim` with `timeout_flagged=true`.
- `sql/ai_timeout_cron.core-sql` — pg_cron job, every minute. Flips visits idle in `still_answering_ai` for 30+ min to `waiting_doctor_claim` with `timeout_flagged=true`.

### Frontend
- `src/app/checkin/[locationId]/CheckinFlow.tsx` — patient state machine. Listens for `summary_ready` broadcast, transitions to `summary_review`. 60-second timer in `generating_summary` state fires `move_to_queue_on_error` if summary never arrives.
- `src/components/patient/SummaryReview.tsx` — displays summary, calls `approve_summary` / `reject_summary` RPC.
- `src/hooks/usePatientRealtime.ts` — realtime + 5s poll fallback. Synthesizes `summary_ready` if `ai_summary` becomes populated while polling.
- `src/components/nurse/NursePatientView.tsx` — nurse triage view. Shows AI summary alongside vitals + nurse-notes input.
- `src/app/(dashboard)/d/nurse/NurseDashboard.tsx` — focus mode auto-claims next patient after release.
- `src/app/(dashboard)/d/doctor/patient/[visitId]/PatientDetailView.tsx` — doctor view. Reads `ai_summary` + `ai_diagnostic` from visit row.
- `src/components/doctor/FocusMode.tsx` — doctor focus mode.

### Configuration
- `locations.nurse_enabled` (boolean) — toggles whether the nurse triage step is part of the flow at this location.
- `locations.diagnostic_enabled` (boolean) — toggles whether `generate-summary` produces a diagnostic at all.
- `locations.ai_model` / `locations.display_format` / `locations.ai_message_limit` / `locations.ai_custom_instructions` — per-location AI tier and output configuration.
- `visits.ai_model_override` / `visits.ai_session_instructions` — per-visit overrides set by receptionist.
- `visits.demo_features.nurseEnabled` — demo-only toggle, propagated to `locations.nurse_enabled` via `sync_demo_location_features` RPC.

## Dependencies

### What this relies on
- `pg_net` extension for fire-and-forget HTTP calls from SQL functions to edge functions.
- `supabase_vault` for `edge_function_url`, `internal_edge_secret`, `supabase_anon_key` secrets.
- AI provider adapters (`supabase/functions/_ai-providers/`) for Claude / Gemini / OpenAI calls per location's tier.
- `get_visit_vitals_text` RPC for nurse vitals fetch in diagnostic prompt.
- `update_medications` / `update_allergies` / `update_chronic_conditions` / `update_pets` RPCs for medical record extraction.
- `move_to_queue_on_error` RPC for failure recovery.
- Translation edge function (`supabase/functions/translate/`) for non-English summary translation in `full` / `summary_only` modes.

### What relies on this
- Doctor / nurse dashboards display `ai_summary` + `ai_diagnostic` from visit rows.
- `complete_visit` SQL function reads `ai_summary` for visit summary SMS to patient.
- Generate-summary's medical record updates feed into next visit's returning-patient context (`start_ai_conversation` reads patient_medications / etc.).
- Past visit summaries (10 most recent) are pulled into both conversation system prompt and diagnostic prompt.

## Testing

### What is covered
- **Manual e2e demo run, non-nurse location**: AI completes → patient sees summary → approves → doctor claims → sees both summary + diagnostic. Logs show one `generate-summary` invocation in `mode: full`.
- **Manual e2e demo run, nurse-enabled location, normal path**: AI completes → patient sees summary → approves → nurse claims → records vitals (e.g., BP 180/110) + notes → releases → doctor claims → diagnostic mentions the elevated BP. Logs show two invocations: `mode: summary_only` then `mode: diagnostic_only`.
- **Manual e2e demo run, nurse-enabled location, doctor goes direct**: Patient approves → doctor (no nurse role) claims before any nurse touches it → logs show `mode: summary_only` then `mode: diagnostic_only` from `claim_patient`. Diagnostic populated, no nurse data referenced.
- **Idempotency**: Re-firing `generate-summary` with `mode: summary_only` against a visit that already has `ai_summary` returns 200 with `skipped: "summary_already_exists"`. Re-firing `mode: diagnostic_only` regenerates (last writer wins).
- **`approve_summary` strictness**: Calling against a visit not in `still_answering_ai` returns `Visit is not in AI conversation state`.

### What needs manual verification
- Doctor-with-nurse-role-too edge case: when a staff member with both roles claims a nurse-enabled visit, they're treated as a nurse claim and the diagnostic is deferred until they release. Verify by claiming as such a user and checking `ai_diagnostic` stays NULL until release.
- Patient timeout (60s): patient never approves → frontend `move_to_queue_on_error` fires → status flips with `timeout_flagged=true`, `approve_summary` returns clean error.
- `reject_summary`: patient rejects → `ai_summary`, `ai_diagnostic`, `ai_completed_at` all clear → patient continues chat → new AI complete → new summary generated.
- AI marker compliance: monitor visits where the AI fails to emit `[CONVERSATION_COMPLETE]` (these stall in `still_answering_ai` until 60s frontend timeout). Strengthen prompt further if rate is non-trivial.
- Translation path: non-English patient (`patients.language != 'en'`) gets a translated summary via the `translate` edge function during `full` / `summary_only` modes only.

## Known limitations

- If the AI fails to emit `[CONVERSATION_COMPLETE]`, the entire pipeline stalls. The 60-second frontend timeout + cron fallback eventually move the visit to the queue, but no summary is generated until a doctor claims the visit (which then triggers the `mode: full` fallback in `claim_patient`). The `start_ai_conversation` system prompt contains a strongly-worded `CONVERSATION END PROTOCOL` block to minimize this, but model regressions can re-introduce the failure mode.
- "Nurse claims and never releases" is an unresolved stuck state — visit sits in `claimed_by_doctor` indefinitely with `ai_diagnostic` NULL. No unclaim or transfer mechanism today.
- `pg_net` queues HTTP requests asynchronously; if the worker is backlogged, diagnostic generation can be delayed by several seconds after `nurse_release_to_doctor`. Doctor opening the visit immediately after release may briefly see a missing diagnostic.
- Generate-summary in `diagnostic_only` mode reads the existing `ai_summary` from the visit row, NOT the original AI summary at the time of generation. If `reject_summary` was called and a new summary was generated mid-flow, the diagnostic uses the most recent summary.
